## Child process environment isolation

The Supervisor now creates each managed process environment through
`ChildEnvironmentBuilder`, rather than passing its full `process.env` to child
applications. Only essential OS variables are inherited. Business values come
from per-application configuration; runtime and ARM injection variables are
assigned by the Supervisor. Reserved keys are validated and rejected.

The Supervisor root `.env` `PORT=3100` no longer overrides the HTTP port of
singleton managed applications. See [Child Environment Builder](docs/CHILD_ENVIRONMENT_BUILDER.md).

## Environment configuration (.env)

All Supervisor and example entrypoints automatically load `.env` from the
repository root using `dotenv`. Set real secrets in an ignored local file:

```bash
cp .env.example .env
# Edit .env, including ARM_MANAGEMENT_TOKEN (16+ characters).
npm install
npm run build
npm run dev:management
```

Host/container environment variables take precedence over the `.env` file.
Leave `ARM_CLIENT_BRIDGE_APP_ID` and `ARM_BLUE_GREEN_APP_ID` empty to disable
those opt-in modes. For Phase 9, fill `ARM_CLIENT_BRIDGE_APP_ID` and both
distinct bridge tokens. Per-child runtime variables (`ARM_INSTANCE_ID`,
`ARM_BRIDGE_MODULE_PATH`, etc.) are generated by the Supervisor, not configured
in `.env`.

See [Environment Configuration](docs/ENV_CONFIGURATION.md).

## Phase 9 — ARM Client Runtime Bridge (opt-in)

Node child processes can now start the **actual ARM Client SDK** through a
Supervisor-owned `--import` preload. App ZIP files do not need `arm-client`
dependencies. SDK registration and metrics WS/HTTP endpoints use existing
ARM contracts and distinct per-instance ports.

```bash
npm run build
export ARM_MANAGEMENT_TOKEN='replace-with-a-long-random-secret'
export ARM_CLIENT_BRIDGE_APP_ID='payment-service'
export ARM_BRIDGE_REGISTRATION_TOKEN='distinct-registration-secret-123'
export ARM_BRIDGE_METRICS_TOKEN='distinct-metrics-secret-456'
npm run dev:management
```

Inspect `GET /runtime/bridge/applications` with the management bearer token.
This does not automatically supply business component registration or readiness.
See [Phase 9 guide](docs/PHASE_9_ARM_CLIENT_RUNTIME_BRIDGE.md).

## Phase 8 — Supervisor-owned ARM runtime preload (opt-in)

The Supervisor can inject a lightweight Node.js instrumentation runtime into new
child processes **without modifying uploaded ZIP files or app dependencies**.

```bash
export ARM_MANAGEMENT_TOKEN='replace-with-a-long-random-secret'
export ARM_AUTO_INJECT=1
npm run dev:management
```

Runtime snapshots are stored at `supervisor-data/telemetry/<instanceId>.json` and
can be read via `GET /runtime/instances/:id/telemetry` with the management token.

This implements process and native HTTP diagnostics instrumentation; it **does not
yet implement the complete arm-client SDK contract or business readiness**.
See [Phase 8 guide](docs/PHASE_8_AUTO_RUNTIME_INJECTION.md).

## Phase 7 — Blue/Green HTTP deployment (opt-in)

A stable localhost HTTP proxy routes to separate Blue/Green Node.js processes,
each with its own port and verified PID. New HTTP requests switch to a healthy
candidate while in-flight requests drain on the previous backend.

```bash
export ARM_MANAGEMENT_TOKEN='replace-with-a-long-random-secret'
export ARM_BLUE_GREEN_APP_ID='payment-service'
export ARM_PROXY_PORT=3400
export ARM_BLUE_PORT=3401
export ARM_GREEN_PORT=3402
npm run dev:management

# Other terminal — both releases must already be installed:
curl -X POST http://127.0.0.1:3300/blue-green/deploy \
  -H "Authorization: Bearer $ARM_MANAGEMENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version":"1.0.0"}'

# Client-facing endpoint:
curl http://127.0.0.1:3400/health
```

The one-time migration away from a direct-port singleton process requires
maintenance. WebSocket upgrade migration and Supervisor-process restart with
uninterrupted TCP connections are **not supported**.

See [Phase 7 Blue/Green guide](docs/PHASE_7_ZERO_DOWNTIME_DEPLOYMENT.md).

## Phase 6 — Transactional Deployment & Safe Rollout

With the management daemon running, release switching can be executed as one
checkpointed operation instead of separate stop / activate / start calls:

```bash
curl -X POST http://127.0.0.1:3300/applications/payment-service/rollout \
  -H "Authorization: Bearer $ARM_MANAGEMENT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"version":"1.1.0","allowProcessOnly":true}'
```

The `allowProcessOnly` flag is **only for test packages without ARM readiness**.
Instrumented apps must reach healthy readiness and stay running through a
stability window. A failed rollout attempts to restore the previous release.
Supervisor startup replays interrupted journal entries conservatively.

See [Phase 6 rollout guide](docs/PHASE_6_TRANSACTIONAL_DEPLOYMENT.md).

## Phase 5 — Deployment API & Release Management

With the management daemon running, authorized localhost clients can install ZIP
artifacts, list releases, activate a stopped app's release, roll back to a
previously active release, and inspect the append-only deployment audit:

```bash
curl -X POST http://127.0.0.1:3300/deployments/upload \
  -H "Authorization: Bearer $ARM_MANAGEMENT_TOKEN" \
  -H "Content-Type: application/zip" \
  --data-binary @payment-service-1.0.0.zip
```

See [Phase 5 deployment API guide](docs/PHASE_5_APPLICATION_DEPLOYMENT_API.md).
Release switches require an already-stopped process. Uploading a ZIP does not
automatically start the new application.

## Phase 4 — Durable Runtime State & Recovery Policies

The management daemon now supplies a `RuntimeStateStore` to the monitor.
Desired process state, recovery attempts and scheduled retries survive Supervisor
restarts and are stored in `supervisor-data/applications/<id>/runtime-state.json`.
An observed exit code 0 is treated as completion for `on-failure` policies.
The retry budget resets only after a configurable stable-running period.

See [Phase 4 guide](docs/PHASE_4_DURABLE_RUNTIME_STATE.md).

## Phase 3 — Runtime monitoring and recovery

Run the management daemon after installing/activating an application:

```bash
export ARM_MANAGEMENT_TOKEN='replace-with-a-long-random-secret'
npm run dev:management
```

The loopback management API supports authenticated list/inspect/activate/start/stop/restart operations.
When started via the API, managed applications are monitored for unexpected process exits and
restarted with bounded exponential backoff according to their manifest. Manual stop suppresses
recovery. Process state and ARM readiness are separate.

See [Phase 3 guide](docs/PHASE_3_APPLICATION_RUNTIME_MONITORING.md).
Avoid using the standalone `app:manage` CLI concurrently with the management daemon
against the same state files.

## Phase 2 — Installed application lifecycle

Installed ZIP applications can now be selected and managed by the Supervisor:

```bash
npm run deploy:zip -- ./supervisor-data/uploads/payment-service-1.0.0.zip
npm run app:manage -- activate payment-service 1.0.0
npm run app:manage -- start payment-service
npm run app:manage -- inspect payment-service
npm run app:manage -- restart payment-service
npm run app:manage -- stop payment-service
```

Phase 2 keeps the selected release across Supervisor restarts and uses the
existing safe `ProcessManager` PID verification. See
[Phase 2 lifecycle guide](docs/PHASE_2_APPLICATION_PROCESS_LIFECYCLE.md).
The Phase 1 payment-service fixture does not expose ARM health: its readiness
status is `NOT_CONFIGURED`.

# base-arm-app — Application Reliability Manager (Phase 4)

Reusable process-local Application Reliability Manager components implemented in TypeScript. Includes HTTP JSON and WebSocket reporting; no user interface.

## Quick start

```bash
npm install
npm run dev
npm test
npm run build
```

The server binds to `127.0.0.1:3100` by default. Configure `ARM_METRICS_TOKEN` to require `Authorization: Bearer <token>` for HTTP and WebSocket upgrade requests. Do not expose endpoints without TLS, authentication and network controls.

## HTTP endpoints

- `GET /metrics`: current metrics snapshot.
- `GET /metrics/:name`: individual metric.
- `GET /reliability/components`: component states.
- `GET /reliability/ready`: readiness (200 when ready, 503 otherwise).
- `GET /reliability/events?since=0`: bounded recent recovery and lifecycle history.

## WebSocket

Connect to `ws://127.0.0.1:3100/metrics/ws`. Commands:

```json
{"action":"snapshot","names":["process.uptime_seconds"]}
{"action":"subscribe","names":["process.memory.rss_bytes"]}
{"action":"unsubscribe"}
{"action":"subscribe_events"}
{"action":"unsubscribe_events"}
```

Snapshots arrive immediately on subscription, followed by periodic metrics updates. Recovery events are streamed as `reliability_event` messages.

## Modules

- `packages/core/src/metrics.ts`: bounded metric registry and Node process collector.
- `packages/core/src/reliability.ts`: component registration, lifecycle, health monitoring, recovery coordination, readiness and event history.
- `packages/adapter-http/src/server.ts`: HTTP REST + WebSocket transport.
- `examples/nodejs-api/src/index.ts`: demonstration application.
- `tests/`: registry, HTTP/WS and reliability tests.

## Limitations

This is a starter implementation and must be hardened before production use.

- Metrics, events and recovery counters are process-local and reset on restart.
- Timeout rejects a Promise but does not cancel an underlying component operation.
- Recovery has per-operation timeout, single-flight and bounded attempts per invocation, but no cross-cycle retry budget, cooldown or fencing.
- Event history is in-memory and bounded, not durable.
- No multi-instance aggregation, persisted time series, or UI.
- `process.cpu.percent_of_one_core` may exceed 100% for multi-core workloads.
- `host.*` metrics reflect OS-visible resources, not necessarily container limits.

Run `npm test` and `npm run build` after installing dependencies; these checks were not verified during initial generation because package installation timed out.

## Phase 4 — Recovery Safety

ARM now includes cooperative `AbortSignal` cancellation, generation-based
operation fencing, prevention of overlapping lifecycle operations, and bounded
graceful shutdown with explicit reporting of blocked components. See
[Phase 4 documentation](docs/PHASE_4_RECOVERY_SAFETY.md).

Adapters that perform external side effects should use `context.assertCurrent()`
before committing state. ARM cannot forcibly cancel uncooperative promises.

## Phase 5 — Integration & Reliability Testing

A generic connection adapter is available at
`packages/adapters/src/reconnectable-resource.ts` for swapping healthy
Database or WebSocket sessions while honoring ARM operation fencing.

Integration scenarios: `tests/integration-reliability.test.ts`.
See [Phase 5 instructions](docs/PHASE_5_INTEGRATION_TESTING.md).

To run: `npm install && npm run build && npm test`.

## External Node.js Process Supervisor

The optional `adapter-process` module launches detached Node.js apps, persists PID records, adopts verified Linux processes after Supervisor restart, and connects to each application's existing ARM `/metrics/ws` endpoint.

See [Process Supervisor documentation](docs/PROCESS_SUPERVISOR.md) and `examples/supervisor/src/index.ts`.

```bash
npm install
npm run build
node dist/examples/supervisor/src/index.js
```

Ctrl+C stops the Supervisor and WebSocket collectors, **not the detached app**. Process restart is explicit; WebSocket disconnection alone does not restart an app.

## Dynamic self-registration of external apps

An independently started ARM-enabled Node.js application can register itself with the Supervisor registration API, after which the Supervisor connects to its ARM `/metrics/ws` endpoint. This provides **monitor-only** visibility and does not authorize process stop/restart.

See [Dynamic Registration](docs/DYNAMIC_REGISTRATION.md).

```bash
# Terminal 1
SUPERVISOR_REGISTRATION_TOKEN=development-secret npm run dev:registration
# Terminal 2
SUPERVISOR_REGISTRATION_TOKEN=development-secret PORT=3101 npm run dev
```
